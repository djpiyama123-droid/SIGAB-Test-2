# SIGAB v4.0.29

**Fecha:** 2026-07-09
**Tipo:** patch (fix)
**Autor:** sesion-sonnet-asus

## Qué cambió

Gustavo reportó (video de producción v4.0.23, 2026-07-09) que "las OS" y la
"orden rápida" no funcionan bien: el modal "Nueva Orden de Servicio" se abrió
2 veces desde la ficha técnica del equipo sin evidencia de creación exitosa,
el botón "⚡ Acción Rápida (OS abierta del equipo)" no parecía llevar a
ningún lado, y el expediente del equipo (`equipoId=1552`) mostraba "Sin
órdenes registradas". Se diagnosticó el flujo completo por código y se
reprodujo con Playwright + mocks de red (harness desechable, sin backend).
Se encontraron y corrigieron **3 causas raíz reales**, todas en frontend
(el payload/endpoint de creación de OS en `routes/ordenes.py` está bien
alineado con lo que manda el modal — no se tocó backend):

### A) Toast de éxito/error desaparecía en ~600ms en vez de sus 6000ms (causa más probable de "sin evidencia")

- **`sigab-frontend/src/lib/toast.js`**: el patrón `const tid =
  toast.loading(...)` seguido de `toast.success(msg, { id: tid })` —usado en
  `OrdenServicioRapidaModal.jsx`, `Ordenes.jsx` (crear/cerrar OS),
  `HospitalMap.jsx` (Acción Rápida) y muchos otros lugares del proyecto—
  hacía que el toast de reemplazo se auto-eliminara casi al instante.
  Causa real: `normalize()` nunca pasaba un `id` explícito a Sileo, así que
  **todo** toast sin id explícito recibía el mismo id interno por defecto
  de la librería (`"sileo-default"`, ver `sileo/dist/index.mjs
  createToast()`). Al hacer `toast.error(msg, { id: tid })`, el adapter
  llamaba `sileo.dismiss(tid)` (que programa un borrado diferido ~600ms
  después de *cualquier* toast con ese id) y acto seguido creaba el toast
  de reemplazo — que, por el mismo bug, terminaba con el **mismo** id
  `"sileo-default"`. El borrado diferido del toast viejo eliminaba
  entonces al toast nuevo a los ~600ms, sin importar su `duration` real.
  Fix: cada llamada (`success`/`error`/`info`/`warning`/`loading`) genera
  ahora un id propio único (`genId()`) y nunca reutiliza el id que se
  está reemplazando. Confirmado con Playwright: antes del fix, el toast de
  error vivía ~600-1000ms; después, los 6000ms completos.

### B) Payload de creación con slash final inconsistente (POST/GET a `/ordenes`)

- **`sigab-frontend/src/api/sigab.js`**: `crearOrden` y `getOrdenes`
  llamaban a `/ordenes` (sin slash final), pero el backend registra la
  colección como `@router.get("/")` / `@router.post("/")` bajo el prefijo
  `/api/ordenes` (`routes/ordenes.py`) — la ruta real es `/api/ordenes/`.
  Confirmado con `TestClient` que esto dispara un **307 redirect** en cada
  creación y cada listado de órdenes: un round-trip extra e innecesario, y
  fràgil detrás de proxies que no reescriban el header `Location` al
  hostname público (mismo patrón de riesgo que causó bugs de mixed-content/
  CORS en otros despliegues dockerizados de FastAPI). Fix: ambas llamadas
  usan ahora `/ordenes/` directo, sin redirect.

### C) Botón "Acción Rápida (OS abierta del equipo)" navegaba a query params que nadie procesaba

- **`sigab-frontend/src/pages/Ordenes.jsx`**: `HospitalMap.jsx`
  (`handleAccionRapida`) navega a `/ordenes?ordenId=X` (si hay una sola OS
  abierta) o a `/ordenes?equipoId=X&estado=abierta` (si hay varias) — pero
  `Ordenes.jsx` no importaba `useSearchParams` ni leía **ningún** query
  param: el mismo patrón de bug que `?accion=nuevo` en `/preventivos`
  (tampoco procesado, confirmado durante el diagnóstico, fuera de alcance
  de este fix). El usuario terminaba en la lista genérica de OS, sin la
  orden abierta automáticamente ni el filtro de equipo aplicado. Fix:
  efecto de un solo uso que lee `ordenId`/`equipoId`/`estado` al montar,
  abre `OrdenDetalleModal` directo si hay `ordenId`, aplica `estado` a los
  botones de filtro existentes y aplica `equipoId` como filtro
  `equipo_id` (el backend ya lo soportaba en `listar_ordenes`, solo
  faltaba conectarlo) — con un chip "Equipo #N ✕" para quitarlo. La URL
  se limpia después de consumirla (`setSearchParams({}, {replace:true})`)
  para no reaplicar el filtro en cada refresco.

### D) Catch silencioso en el expediente del equipo ("Sin órdenes registradas" sin distinguir vacío de error)

- **`sigab-frontend/src/components/EquipoDetail.jsx`**: `recargarHistorial()`
  (`GET /equipos/{id}/historial`) y el efecto de `getExpedienteEquipo`
  (`GET /equipos/{id}/expediente`) terminaban en `.catch(() => {})` —
  cualquier fallo (401, 500, red) se tragaba en silencio y la sección
  "Tickets / Órdenes de Servicio" mostraba "Sin órdenes registradas",
  indistinguible de un equipo genuinamente sin historial. Fix: ambos
  catches ahora hacen `console.error` + `toast.error` (no bloquean el
  render — la sección sigue mostrando lo que haya, pero el fallo ya no es
  invisible).

## Por qué

El video no traía captura del error exacto, así que se reprodujo el flujo
completo con un harness desechable de Playwright + mocks de red (sin
backend/DB real) montando los componentes reales (`OrdenServicioRapidaModal`,
`EquipoDetail`, `Ordenes.jsx` con `MemoryRouter`) contra respuestas
controladas de éxito, 422/500 y timeouts. Esto permitió medir el tiempo de
vida real del toast (no solo leer el código) y confirmar los 4 hallazgos
con evidencia reproducible en vez de conjeturas.

## Qué verificar

1. Crear una OS desde la ficha técnica del mapa (botón "Abrir Orden de
   Servicio"): el toast de éxito ("Orden OS-... creada") debe permanecer
   legible varios segundos, no un parpadeo. Repetir forzando un error de
   red/backend: el toast de error debe permanecer igual de legible y el
   modal debe quedarse abierto para reintentar.
2. Network tab: `POST` de creación de OS debe ir directo a
   `/api/ordenes/` (con slash), sin un 307 previo a `/api/ordenes`.
3. Desde la ficha técnica de un equipo con una sola OS abierta, click en
   "⚡ Acción Rápida": debe abrir directo el detalle de esa OS en
   `/ordenes`. Con varias OS abiertas: debe aterrizar en `/ordenes` con el
   filtro "abierta" activo y un chip "Equipo #N" visible; quitar el chip
   debe volver a mostrar todas las órdenes.
4. Forzar un error 500 en `/equipos/{id}/historial` o `/expediente` (con
   un equipo real que sí tenga órdenes): debe aparecer un toast de error
   explícito en vez de mostrar "Sin órdenes registradas" en silencio.
5. `npm run build` y `npx vitest run` en `sigab-frontend/` deben quedar
   verdes (22 tests, sin regresiones).

## Cómo revertir

`git revert` de los commits de esta versión sobre
`fix/os-flujo-2026-07-09` antes de mergear, o revert + redeploy de
frontend si ya se mergeó. Todos los cambios son de frontend (adapter de
toasts, cliente HTTP, un page component y un modal); no tocan esquema de
base de datos ni requieren rollback de backend.
