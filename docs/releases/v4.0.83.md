# v4.0.83 — Reservas ya no muestra datos falsos en producción

**Fecha:** 2026-07-24 · **Tipo:** patch · **Commit:** `8265e3c` · **Autor:** loop-thinkcentre

## Qué cambió

La página **Reservas de Equipos** tenía un comportamiento heredado de la
etapa de diseño/tuning del dashboard: si la API devolvía una lista vacía de
reservas, o si la petición fallaba (backend caído, red intermitente), la
página sustituía silenciosamente los datos reales por **160 reservas
inventadas** — nombres de médicos ficticios ("Dr. Hernández", "Dra.
Ramírez"), equipos biomédicos reales del catálogo (ventiladores,
desfibriladores, monitores) y motivos como "Cirugía programada" o
"Traslado de paciente crítico". El único aviso de que eran datos falsos era
una pequeña píldora ámbar de 11px dentro de un párrafo de subtítulo.

## Por qué importa

SIGAB corre como **piloto real** en el HGR No. 1 IMSS Tijuana — no es una
demo. Si la base de reservas estaba vacía en un momento dado (instalación
nueva, o simplemente ningún equipo reservado ese día) o había un problema
de red momentáneo, cualquier persona del hospital que abriera Reservas veía
un calendario y una lista de "reservas" de equipos que **nunca ocurrieron**,
atribuidas a nombres de doctores inventados. En un sistema clínico esto no
es un detalle cosmético: puede generar confusión operativa real sobre la
disponibilidad de equipo.

## Qué se hizo

- Se eliminó por completo el fallback a `generarReservasMock()`
  (`utils/reservasMock.js`).
- Una lista vacía **real** ahora se muestra vacía: el heatmap y las
  tarjetas de estadísticas ya soportan 0 reservas sin romperse (cubierto
  por el test existente de `fechas.test.js`).
- Un error real de red/backend ahora muestra un banner de reintento
  explícito (ícono + mensaje + botón "Reintentar"), mismo patrón ya usado
  en el Mapa de Activos (`HospitalMap.jsx`).
- Se quitó el estado `usandoMock` y la píldora "datos de muestra" del
  encabezado.

## Qué verificar

1. Con reservas reales sembradas: Reservas debe verse exactamente igual
   que antes (heatmap, gráfica de 30 días, tarjetas de estadísticas).
2. Con la lista vacía (o un tenant sin reservas): ya NO debe aparecer
   ninguna reserva falsa ni la píldora ámbar — el heatmap y las tarjetas
   deben mostrarse en cero, sin error.
3. Con el backend caído o la red cortada momentáneamente: debe aparecer
   un banner rojo "No se pudo cargar la actividad de reservas..." con
   botón "Reintentar" que recarga los datos reales al reconectar.
4. El heatmap semanal y el flujo de "Nueva Reserva"/"Editar Reserva"
   (regla dura del proyecto) deben seguir funcionando sin cambios.
