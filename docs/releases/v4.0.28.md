# SIGAB v4.0.28 — 2026-07-09

> Nota de versionado: build interno de la rama `fix/copilot-health-apimode-2026-07-09`.
> El número final se renumerará al mergear a `v4.0/piloto-clinica-1` si para
> entonces ya existe una versión mayor en esa rama.

## Qué cambió

Bug de producción visto en el video de v4.0.23: `/copilot` mostraba el badge
"Ollama offline" y el banner "Ollama no detectado — instala Ollama en el
servidor (Lenovo ThinkCentre)..." de forma permanente, aunque desde
2026-07-04 el chat de texto corre contra la API de MiniMax
(`SIGAH_LLM_API_MODE=api`) y Ollama solo se usa para OCR/visión.

**Causa raíz:**
- `sigab-backend/services/gemma_service.py` función `verificar_ollama()`:
  en modo API devolvía `ollama_activo: false` fijo (correcto, Ollama no se
  usa ahí) pero sin ningún campo que indicara el modo activo, y sin
  verificar de verdad la salud del proveedor en la nube (`ok: True` fijo,
  nunca se detectaba un MiniMax caído). Además, si Ollama respondía con un
  status distinto de 200 (sin lanzar excepción), la función no retornaba
  nada (`None` implícito) — un 500 en el endpoint `/estado`.
- `sigab-frontend/src/pages/Copilot.jsx`: el badge, los banners y el
  subtítulo decidían todo a partir del campo `ollama_activo`, que el backend
  fija en `false` siempre en modo API — de ahí que el banner de "instala
  Ollama" apareciera también con el proveedor en la nube sano.

**Fix:**
- Backend: `verificar_ollama()` ahora retorna `{ok, mode: "api"|"ollama",
  detail, ...}`. En modo API hace un `GET {LLM_API_BASE}/models` real (5s
  timeout) para detectar si el proveedor en la nube está accesible. En modo
  Ollama se agregó el `return` que faltaba para el caso de status ≠ 200.
- Frontend: nueva función pura `estadoCopilot(status)` en
  `sigab-frontend/src/pages/copilotEstado.js` (separada de `Copilot.jsx`
  para poder testearla con vitest sin jsdom) que decide badge/banner a
  partir de `{mode, ok, modelo_disponible}`. El banner "instala Ollama" solo
  sale si `mode==="ollama"` y está caído; `mode==="api"` caído muestra
  "Proveedor de IA en la nube no disponible" con el `detail` del backend;
  `mode==="api"` sano no muestra banner y habilita el chat. El subtítulo
  "IA local on-premise" ahora es dinámico ("IA en la nube" en modo API). Se
  quitó la mención a "Lenovo ThinkCentre" del texto (ahora "servidor edge
  del hospital"). De paso se corrigió `ollamaStatus.modelo` (campo
  inexistente — el backend nunca lo mandó) por `ollamaStatus.modelo_activo`
  en el badge y en el panel de configuración del modelo.
- No se tocó el pipeline de OCR/visión (`_vision_client`, `analizar_imagen`)
  ni el filtro `<think>` de MiniMax (`_strip_think`).

## Shape final de `GET /api/copilot/estado`

```json
{
  "ok": true,
  "mode": "api",
  "detail": null,
  "ollama_activo": false,
  "modelo_configurado": "MiniMax-M2.5",
  "modelo_activo": "MiniMax-M2.5",
  "modelo_disponible": true,
  "modelos_instalados": [],
  "copilot_habilitado": true
}
```
`detail` viene poblado solo cuando `ok=false`, con un mensaje humano sin
nombres de hardware.

## Qué verificar

1. Con `SIGAH_LLM_API_MODE=api` y el proveedor sano: sin banners, badge
   verde "`<modelo>` · activo", subtítulo "IA en la nube".
2. Con `SIGAH_LLM_API_MODE=api` y el proveedor caído (o `SIGAH_LLM_API_KEY`
   vacío/URL mala): badge rojo "IA en la nube no disponible" + banner rojo
   con el detalle del error — nunca el texto de instalar Ollama.
3. Con `SIGAH_LLM_API_MODE=ollama` y Ollama caído: badge rojo "IA local
   offline" + banner naranja de instalación, ahora sin mencionar

4. `npm run build` y `npx vitest run` verdes; `python3 -m py_compile` +

## Post-deploy pendiente (fuera de este cambio de código)

Verificar en el VPS que el contenedor del backend tiene
`SIGAH_LLM_API_MODE=api` (o `openai`, según el nombre usado en ese entorno)
y `SIGAH_LLM_API_KEY` con la key de MiniMax cargados — si faltan,
`_OPENAI_MODE` da `False` y el backend cae al branch de Ollama aunque el
código ya esté corregido. Esto no se puede verificar desde este worktree
(sin acceso al VPS); revisar `docker compose exec <servicio-backend> env |
grep SIGAH_LLM` y `docker compose restart <servicio-backend>` tras corregir.

## Cómo revertir

```
git revert a0c6a6a
```
sobre `v4.0/piloto-clinica-1`. Cambio de backend (un endpoint de solo
lectura) + frontend (banners/badge), sin migraciones de base de datos —
revert seguro. Rollback funcional alternativo si el problema es de
configuración: `SIGAH_LLM_API_MODE=ollama` + restart del backend (no
requiere revertir este código).
